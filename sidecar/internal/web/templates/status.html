A stale VACUUM silently truncates HNSW index scans — a high or climbing number here, not just search results that seem short, is the sign to check.

Passages per entry is the ratio that makes disk growth predictable: the design spec assumed 4–6 and measured 13, which put its sizing estimate off by roughly 5x. Passage and entry counts are estimates (Postgres' own planner statistics, refreshed by ANALYZE/autovacuum), not an exact count — cheap to read regardless of corpus size. Autovacuum's analyze threshold scales with the table's own size, not with elapsed time, so on a fast-growing table this estimate can lag well behind the real count, not just briefly; right after a table is first created it has no estimate to show at all, marked distinctly above rather than shown as a plain zero.

Changing the model changes every stored passage's expected content hash, so the whole corpus becomes pending and is re-embedded from scratch — minutes for a small corpus, hours at real scale. The one exception: the same model running on another machine needs no re-index, but only if the candidate reports an identity identical to the one active now — and it will not by default, because a local model's identity is a sha256 of the model file while a remote's is whatever that server reports. In practice, switching local → remote re-indexes unless the remote is deliberately configured to report the same identity.
