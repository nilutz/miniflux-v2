# P1b Search Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the populated index into working search — BM25, vector, and RRF-fused hybrid retrieval, with similar-article suggestions, surfaced in the Miniflux reader.

**Architecture:** Retrieval lives in the sidecar as a new `internal/search` package over the existing `search.passages` table, exposed by an HTTP API. The Miniflux fork's search page calls it, and falls back to its existing entry-level FTS when the sidecar is unreachable.

**Tech Stack:** Go 1.27, PostgreSQL 18 via ParadeDB (`pg_search` 0.25.9, `vector` 0.8.4), the pinned hugot/ONNX embedder.

**Spec:** `docs/superpowers/specs/2026-09-12-miniflux-search-design.md` — §6.2 through §6.5, §7, §8.2 and §8.3 bind this plan. §11 requires the evaluation set this plan opens with.

## The RRF query shape — validated against this schema

This ran correctly against the live database and is the pattern to build on:

```sql
WITH lexical AS (
    SELECT id, row_number() OVER (ORDER BY paradedb.score(id) DESC) AS rnk
    FROM search.passages WHERE text @@@ $1 LIMIT $2
), semantic AS (
    SELECT id, row_number() OVER (ORDER BY embedding <=> $3::vector) AS rnk
    FROM search.passages ORDER BY embedding <=> $3::vector LIMIT $2
)
SELECT COALESCE(l.id, s.id) AS id,
       COALESCE(1.0/(60 + l.rnk), 0) + COALESCE(1.0/(60 + s.rnk), 0) AS rrf
FROM lexical l FULL OUTER JOIN semantic s ON l.id = s.id
ORDER BY rrf DESC;
```

`60` is the conventional RRF *k*. Keep it a named constant.

## Two constraints that will bite if you forget them

**Highlighting depends on re-deriving plaintext.** `char_start`/`char_end` index into `passage.ExtractText(entry.content)`, which is **never stored**. Any consumer of offsets must call `ExtractText` on the current content and must check `store.PipelineVersion` still matches the entry's recorded state — otherwise the offsets refer to a plaintext that no longer exists and highlighting silently lands on the wrong words.

**`passages_bm25_idx` covers only `(id, text)`.** A BM25 query filtered by feed, date or status cannot push those predicates into the index and falls back to a join. Retrieve a generous candidate set from BM25, then filter — do not expect the index to do it.

### Task 1.5: Index entry titles

**Files:**
- Modify: `sidecar/internal/store/migrations.go` (append a migration), `sidecar/internal/store/entries.go`
- Modify: `sidecar/internal/indexer/indexer.go`, `indexer_test.go`

**Interfaces:**
- Consumes: Task 1's corpus (re-indexed after this lands)
- Produces: `search.passages.source` (`'title'` | `'content'`); title passages in the index

**Why this exists.** `EntryForIndexing` selects only `content`, so **entry titles are not indexed at all**. A post headlined "Why Raft is hard" whose body never repeats "Raft" cannot be found by searching for Raft. Miniflux's own FTS weights the title *highest* (`setweight(to_tsvector(title), 'A')` against `'B'` for content), so without this the new hybrid search is **worse than the entry-level FTS it replaces** on precisely the words an author chose most deliberately.

This must land before Task 2, or BM25 retrieval gets built and evaluated against a title-less index.

- [ ] **Step 1: Write the failing tests**

Cover: indexing an entry produces a passage with `source='title'` whose text is the title; body passages carry `source='content'`; an entry with an empty title produces no title passage rather than an empty one; re-indexing replaces both kinds atomically; and a title passage's `char_start`/`char_end` index into **the title**, not the body plaintext.

That last one is the trap. Offsets are only meaningful relative to their source string, and Task 5 will slice by them.

- [ ] **Step 2: Append the migration**

A third entry in `migrations` adding `source text NOT NULL DEFAULT 'content'` to `search.passages`. Append only — never reorder.

Consider whether `passages_bm25_idx` should include `source` so a title-weighted query can filter on it; say what you decided and why.

- [ ] **Step 3: Implement**

`EntryForIndexing` selects `title` alongside `content`. The indexer emits one title passage (ordinal 0, `source='title'`, offsets into the title) followed by body passages (`source='content'`, offsets into the extracted plaintext, ordinals from 1).

Embed the title like any other passage — it is short, so it costs one extra forward pass per entry, which is nothing against 4–6 body passages.

- [ ] **Step 4: Bump `store.PipelineVersion`**

This changes what is indexed, so every existing entry's recorded state is now stale. Bumping the version is what makes the backfill re-index them — the mechanism exists for exactly this. Note in your report that the eval corpus must be re-indexed before Task 2 measures anything.

- [ ] **Step 5: Verify and commit**

Re-index the eval corpus and confirm title passages exist for entries that have titles.

```bash
cd sidecar && make lint
git commit -m "feat(sidecar): index entry titles as their own passages"
```
